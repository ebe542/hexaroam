# Calibration-station protocol

This is the station-specific command contract. Decoding, raw-pulse control and ACK/NACK content generation are implemented in the application's library and covered by host tests. UART framing integration and the production PIO backend are pending; the normal station firmware still performs only startup logging and LED heartbeat.

## Layers and content

The shared protocol crate supplies COBS/CRC32 framing and transport interfaces. Station command semantics live under `src/command.rs`, `src/control.rs` and `src/command_handler.rs`. The handler accepts CRC-validated content and returns response content; it does not perform framing, UART I/O or background output servicing.

The planned UART link uses the existing wire format:

```text
00 | COBS(content | CRC32 little endian) | 00
```

All multibyte parameters and result fields below are little endian. Example bytes in this document are content only, without CRC or COBS delimiters. The station and robot controller are separate protocol endpoints: command 03 and status flags have different application-specific meanings.

## Requests

| Command | Content | Meaning |
| --- | --- | --- |
| GET_STATUS | 01 | Read status flags and the last accepted pulse width |
| OUTPUT_ENABLE | 02 followed by one byte, 00 or 01 | Stop output or start the prepared pulse |
| SET_PULSE | 03 followed by one u32 pulse width in microseconds | Prepare or update a pulse |

Extra or missing parameters are rejected. OUTPUT_ENABLE accepts only 00 and 01. Pulse-range validation belongs to the control service; the initial configured limits are 1000 through 2000 microseconds inclusive. The existing hardware example uses a 20000-microsecond period; the future hardware adapter must preserve this configured period.

The service starts without a prepared pulse. SET_PULSE while inactive prepares a value without touching the hardware. Enabling without a prepared value is rejected. Repeated enable while active succeeds without restarting the output. Disabling stops output and retains the prepared value for a later enable.

Active pulse updates are submitted to the backend. Busy or invalid updates preserve the last accepted value. Period-boundary switching is the responsibility of the PIO backend, not the handler. An ACK confirms acceptance, not a measured pulse edge or actual servo position.

## Responses

| Response | Content |
| --- | --- |
| Successful GET_STATUS | 80 01 followed by status u32 and pulse width u32 |
| Successful OUTPUT_ENABLE | 80 02 |
| Successful SET_PULSE | 80 03 |
| Rejected request | 81 followed by original command byte and one-byte error code |

The status response has ten content bytes; other ACKs have two and NACKs have three. The handler owns a fixed ten-byte response buffer and exposes only its populated prefix. No allocation or caller-provided response buffer is required.

An unprepared pulse is reported as zero with PULSE_READY clear. Once a pulse is prepared, the value is the last accepted request, including while disabled. It is not an actual angle, physical pulse measurement or confirmation that a pending update has already reached the output pin.

## Status flags

| Bit | Name | Meaning |
| --- | --- | --- |
| 0 | PULSE_READY | A valid pulse width has been accepted |
| 1 | RUNNING | Backend reports active output or a completed stop has not been confirmed |
| 8 | OUTPUT_ERROR | A latched backend fault or output-operation failure |

RUNNING describes output lifecycle state, not the instantaneous GP0 level. OUTPUT_ERROR remains set after a successful stop. It blocks enabling and further pulse changes; stopping remains allowed. Recovery requires reinitialization/restart at this stage.

The application loop must call the control service's service() method to advance the backend and latch asynchronously detected faults. The command handler does not implicitly perform this background work.

## NACK codes

| Value | Name | Examples |
| --- | --- | --- |
| 01 | UnknownCommand | Unsupported command byte |
| 02 | InvalidLength | Missing or additional parameters |
| 03 | InvalidValue | Invalid enable byte or pulse outside configured limits |
| 04 | InvalidState | Enable requested before preparing a pulse |
| 05 | Busy | Backend cannot accept the operation yet |
| 06 | OutputError | Output operation failed or an output fault is latched |

Empty input and incoming ACK/NACK content are ignored without responding or changing control state. Invalid COBS/CRC content is rejected outside the handler before dispatch. Unknown requests with a command byte receive a NACK. No unsolicited protocol output is generated by the handler; debug logging remains separate on UART1.

## Content examples

| Request | Response | Effect |
| --- | --- | --- |
| 01 | 80 01 00 00 00 00 00 00 00 00 | Initial status |
| 02 01 | 81 02 04 | Enable rejected without prepared pulse |
| 03 DC 05 00 00 | 80 03 | Prepare 1500 us |
| 01 | 80 01 01 00 00 00 DC 05 00 00 | Prepared, inactive |
| 02 01 | 80 02 | Start prepared output |
| 01 | 80 01 03 00 00 00 DC 05 00 00 | Prepared and running |
| 03 D1 07 00 00 | 81 03 03 | Reject 2001 us; preserve 1500 us |
| 02 00 | 80 02 | Stop; preserve prepared pulse |

These examples are request/response semantics verified through host tests, not serial test vectors already executed on the station.
